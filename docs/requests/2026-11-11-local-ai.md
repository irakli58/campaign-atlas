ATLAS — Complete Local AI Generation, Hardware Detection & Intelligent Model Recommendations
Claude, I want Atlas to support local AI generation as a full alternative to cloud-based AI generation.
My ideal goal is for users to generate campaigns, worlds, stories, NPCs, locations, and other content entirely on their own computers, without depending on paid APIs or an internet connection.
I also want the application to automatically evaluate the user's computer specifications and recommend the best local AI configuration for their hardware.
The goal is to achieve quality as close as possible to Atlas's existing cloud generation, while maintaining reasonable performance.
Do not replace the existing cloud generation systems. Local generation should be an additional option.
1. Audit Existing AI Generation
Before implementing anything, inspect every AI-dependent feature in Atlas.
This includes:

* Campaign generation.
* Story and plot generation.
* NPC generation and dialogue.
* Detective mysteries and clues.
* Fantasy and Sci-Fi Writer Councils.
* DM Copilot.
* Gazetteer assistance.
* Faction and civilization generation.
* Political relationships.
* Dynamic world events.
* Building interior generation.
* Procedural map generation.
* Planet and galaxy generation.
* Handout generation.
* Asset generation.
* Music generation.
* Narration and text-to-speech.
* Session transcription.
* Campaign memory and knowledge management.

Determine which features:

1. Already run procedurally without AI.
2. Already support local AI.
3. Require cloud AI.
4. Could support either local or cloud AI.
5. Would need significant changes to work locally.

Do not replace working procedural generators with AI unnecessarily.
For example, if Atlas can generate realistic planetary orbits using mathematical algorithms, that should continue working without an AI model.
Use local AI for tasks where language understanding, creativity, or reasoning genuinely adds value.
2. Local AI Mode
Add three generation modes to Atlas.
Local AI

* AI inference runs on the user's computer.
* No paid cloud API required.
* Works offline after the necessary models and assets are installed.
* Uses the best compatible local models available.

Cloud AI

* Uses the existing cloud providers and models.
* Preserves all current functionality.
* Does not require downloading large local models.

Hybrid

* Allows different features to use local or cloud AI.
* For example, local NPC dialogue and cloud-based complex story generation.
* Supports automatic fallback only when the user explicitly enables it.

The user should be able to configure a default mode and override it for individual features.
Never silently send campaign data to a cloud service when Local AI mode is selected.
3. Automatic Hardware Detection
I want Atlas to inspect the user's computer and determine what local AI models it can realistically run.
Where permitted by the operating system and application environment, detect:

* CPU model and capabilities.
* CPU core count.
* Installed RAM.
* GPU model.
* GPU VRAM.
* Available storage.
* Supported acceleration technologies.
* Operating system.
* Relevant graphics and compute capabilities.

Investigate support for:

* NVIDIA CUDA.
* AMD ROCm where supported.
* Apple Metal.
* Vulkan-based acceleration.
* CPU-only inference.
* Browser WebGPU where practical.

Be realistic about what information browsers can access.
If Atlas runs in a browser, investigate whether a desktop companion or local inference service is necessary for reliable hardware detection.
Do not claim to detect exact VRAM or GPU specifications if the environment does not expose them.
Allow manual specification entry when automatic detection is unavailable.
4. Intelligent Hardware Recommendations
Based on the detected hardware, Atlas should recommend the best local AI setup.
For example:
Entry-Level Computer

* Lightweight quantized language models.
* CPU-compatible inference where necessary.
* Smaller context windows.
* Lower memory requirements.
* Slower but usable generation.

Mid-Range Gaming Computer

* Medium-sized quantized language models.
* GPU acceleration.
* More complex NPC generation.
* Better story and campaign assistance.
* Larger context windows where practical.

High-End Computer

* Larger reasoning and creative-writing models.
* More complex campaign generation.
* Stronger DM Copilot.
* Longer context support.
* Higher-quality output with acceptable performance.

Workstation

* Large models or multi-model workflows where practical.
* Extensive campaign context.
* Advanced creative generation.
* More demanding local audio and asset workflows.

These are illustrative categories, not fixed hardware thresholds.
Recommendations must be based on actual benchmark results and model requirements.
Example recommendation screen

RAM: Available system memory
Recommended configuration: Balanced Local AI
Suggested models:

* Best Quality.
* Balanced.
* Fastest.
* Low Memory.

Estimated performance:

* Model memory requirements.
* Expected generation speed.
* Approximate storage usage.
* Supported features.

Explain why each model is recommended.

Research current open-weight and locally runnable AI models.
Do not rely on outdated recommendations.
Investigate model families such as:

* Qwen.

* Other competitive models available at implementation time.

Evaluate models for Atlas's specific needs:

Check model licenses, hardware requirements, and commercial redistribution permissions.

Test actual performance and output quality.
6. Local Inference Engines
Investigate suitable local inference systems, including:

* llama.cpp.
* Ollama.
* LM Studio integrations.
* WebLLM.
* ONNX Runtime.
* Other appropriate local inference engines.

Compare their advantages and limitations.
I want Atlas to make local AI as easy to use as possible.
Ideally, the user should not need to manually configure servers, command-line tools, or complicated model paths.
If a local inference engine needs installation, provide a guided setup process.
Do not bundle unnecessary services or large downloads without user consent.
7. Quality Should Be the Priority
I want local generation to be as good as possible.
Don't simply use a tiny model for every task.
Investigate ways to improve local output quality through:

* Better prompting.
* Structured generation.
* Multi-stage generation.
* Planning before writing.
* Self-consistency checks.
* Campaign-specific knowledge retrieval.
* Validation against established lore.
* Genre-specific generation instructions.
* Selective use of reasoning models.
* Multiple passes for complex tasks.

For example, a mystery generator could:

1. Establish the central mystery.
2. Define the actual sequence of events.
3. Create suspects and motivations.
4. Generate clues.
5. Check whether the mystery is solvable.
6. Check for contradictions.
7. Present the final result.

This may allow a smaller local model to produce better results than a single unstructured generation pass.
However, avoid excessive latency.
Provide a fast mode for live sessions and a quality-focused mode for campaign preparation.
8. Local AI DM Copilot
The DM Copilot must support local generation.
It should be able to:

* Understand handmade campaigns.
* Understand generated campaigns.
* Answer questions about established lore.
* Suggest NPC dialogue.
* Help improvise unexpected events.
* Suggest consequences.
* Track campaign developments.
* Assist with encounters.
* Help manage investigations.
* Use the Gazetteer.
* Respect NPC knowledge.
* Respect campaign secrets.
* Understand session history.

Use the same campaign context and knowledge systems as cloud AI.
Do not create a separate, less capable DM Copilot for local mode.
The interface and available tools should remain the same, even if response quality or speed varies with the selected model.
9. Local AI Writer Councils
I also want the genre-specific Writer Councils to work locally.
Investigate whether they can use:

* A shared local model with different specialist prompts.
* Different local models for different roles.
* A hybrid approach when permitted.

For example, the Detective/Horror Council should still help with clues, mysteries, pacing, and atmosphere.
The Sci-Fi Council should still help with scientific plausibility and worldbuilding.
The Fantasy Council should still help with lore, politics, and storytelling.
Do not require several large models to be loaded simultaneously if one model can perform multiple roles effectively.

12. Automatic Benchmarking
Add an optional hardware benchmark.
Instead of relying only on specifications, Atlas should test real inference performance.
For example:

* Tokens generated per second.
* Time to first response.
* Memory consumption.
* Context window performance.
* GPU versus CPU performance.
* Stability under longer prompts.

Use this information to refine recommendations.
Avoid running expensive benchmarks without informing the user.
13. Quality Comparison
I want Atlas to evaluate local generation quality against the existing cloud generation system.
Create a representative test suite covering:

* Fantasy campaign creation.
* Call of Cthulhu mystery generation.
* Sci-Fi campaign creation.
* NPC dialogue.
* Political worldbuilding.
* Story consistency.
* DM Copilot improvisation.
* Structured data generation.
* Long-term campaign continuity.

Compare:

* Creativity.
* Coherence.
* Logical consistency.
* Instruction following.
* Scientific or historical accuracy.
* Campaign lore consistency.
* Generation time.
* Memory usage.

Use reproducible tests and human review where appropriate.
If local generation is noticeably worse than cloud generation for a particular task, be transparent about it.
Recommend the best option rather than claiming identical quality.
14. Smart Task-Based Model Selection
Different tasks may benefit from different models.
For example:

* Fast NPC dialogue: smaller low-latency model.
* Complex mystery generation: stronger reasoning model.
* Long-form campaign writing: strong creative-writing model.
* Structured NPC creation: reliable instruction-following model.
* DM Copilot: model optimized for reasoning, context, and tool use.

Allow Atlas to recommend task-specific models.
However, don't require users to download five different models if one capable model can handle their needs.
Optimize for quality, convenience, and storage.
15. Local Campaign Knowledge & Memory
Local AI must have access to the same campaign information as cloud AI.
Reuse the existing:

* Gazetteer.
* Campaign Knowledge & Readiness Panel.
* NPC knowledge tracking.
* Story and plot systems.
* Faction relationships.
* World state.
* Session memory.
* Handouts.
* Investigation systems.

Investigate local retrieval and indexing for large campaigns.
The DM should be able to use a large handmade campaign without needing to paste the entire story into every prompt.
Ensure retrieval respects DM-only secrets and player-facing visibility.
16. Offline Operation and Privacy
When Local AI mode is enabled:

* AI inference should happen locally.
* Campaign information should not be sent to cloud AI providers.
* Generation should work without an internet connection after setup.
* Downloaded models should be usable offline.
* Clearly distinguish local and cloud features.
* Warn before any action that requires an external service.

Test offline operation rather than merely assuming it works.
17. Seamless Integration
I don't want separate campaign editors for local and cloud AI.
The existing Atlas interface should work with either backend.
For example:
Generate NPC
Generation provider:

* Local.
* Cloud.
* Hybrid.

The resulting NPC should use the same data structures and editing tools regardless of how it was generated.
Switching providers should not change or delete campaign content.
18. Performance and Reliability
Local models can consume significant memory.
Implement safeguards where appropriate:

* Memory-aware model loading.
* Avoiding unnecessary simultaneous model loads.
* Cancellation of generation.
* Progress indicators.
* Handling out-of-memory errors.
* Recovery from failed generation.
* Model unloading when idle.
* Preserving unfinished work.
* Background loading where appropriate.

Do not let local inference freeze the map editor or destroy unsaved campaign data.
19. Implementation Plan
Before making major changes:

1. Audit all AI-dependent features.
2. Identify the existing AI provider architecture.
3. Research current local inference
